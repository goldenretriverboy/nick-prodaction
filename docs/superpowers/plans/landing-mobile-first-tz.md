# ТЗ: Лендинг обучения + страница работ (Mobile-First, контент в приоритете)

Версия: v1.1  
Дата: 16 апреля 2026

## 1. Цель продукта
1. Показать социальное доказательство через общий заработок учеников.
2. Показать реальные работы учеников и вести на страницу с кейсами.
3. Конвертировать трафик в заявки на обучение через тарифы и форму.

## 2. KPI
1. CTR кнопки из 1-го экрана в блок работ: не ниже 20%.
2. CTR кнопки "Смотреть еще" в /works: не ниже 12%.
3. Конверсия из просмотра тарифов в отправку формы: не ниже 6%.
4. Конверсия лендинга в лид: целевое 3-8% (после 2-4 недель данных).

## 3. Страницы и структура
1. Страница / (главная).
2. Страница /works (каталог работ учеников).
3. Политики /privacy, /offer (обязательно для формы и рекламы).

## 4. Информационная архитектура главной /
1. Блок Hero на весь экран (100dvh) с крупной динамической суммой.
2. Блок "Работы учеников" с превью карточек и кнопкой "Смотреть еще".
3. Блок "Тарифы" с 2-4 пакетами.
4. Блок "Форма заявки".
5. Footer с юридической информацией и контактами.

## 5. Контент-модель (без привязки к цветам)
1. Главный месседж: "Ученики уже зарабатывают с ИИ".
2. Крупный показатель: "Общий подтвержденный заработок: {total}$".
3. Дисклеймер под суммой: "Сумма собирается из отчетов учеников и проходит модерацию".
4. Блок работ: "Реальные проекты учеников: что сделали и какой результат получили".
5. Блок тарифов: "Выберите формат обучения под свою цель".
6. Форма: "Оставьте заявку - подберем оптимальный тариф и маршрут старта".

## 6. UX-сценарий пользователя (основной путь)
1. Пользователь открывает / и сразу видит крупную сумму + короткий оффер.
2. Скроллит/жмет CTA в блок работ, оценивает качество кейсов.
3. Переходит в /works через "Смотреть еще" или возвращается на главную.
4. Смотрит тарифы, выбирает подходящий.
5. Отправляет форму.
6. Получает экран "Заявка отправлена" + сообщение о сроке обратной связи.

## 7. Детальная UI-спека (Mobile-First)

### 7.1 Брейкпоинты
1. 360-389 (минимальный mobile).
2. 390-479 (стандартный mobile).
3. 480-767 (large mobile).
4. 768-1023 (tablet).
5. 1024+ (desktop).

### 7.2 Сетка и отступы
1. Базовая ширина проектирования: 390px.
2. Горизонтальные поля: 16px (mobile), 24px (tablet), 32px (desktop).
3. Вертикальный ритм секций: 56px (mobile), 72px (tablet), 96px (desktop).
4. Радиусы: единая шкала 12/16/20.
5. Минимальный тач-таргет: 44x44px.

### 7.3 Типографика
1. H1 в hero: адаптивный clamp(32px, 9vw, 72px).
2. H2 секций: 28px mobile, 36px desktop.
3. Body: 16px, межстрочный 1.4-1.6.
4. Подписи/дисклеймеры: 13-14px.
5. Все числовые значения в сумме с tabular-nums для ровной анимации цифр.

### 7.4 Hero (100dvh)
1. Содержимое центрируется по вертикали и горизонтали.
2. Порядок контента: оффер, крупная сумма, дисклеймер, CTA.
3. Сумма анимируется по сценарию "wow" при первом появлении: count-up от 0 до total за 1.6-2.2s с плавным замедлением к финалу.
4. В конце count-up срабатывает акцент: короткий pulse числа (scale 1 -> 1.06 -> 1 за 250-350ms) и мягкое свечение фона суммы.
5. При поступлении новых подтвержденных сумм во время сессии выполняется micro-update: анимация только дельты (+N$) и плавное увеличение total без перезапуска полного count-up.
6. Полный "wow" запускать только один раз за сессию для текущей страницы, чтобы не утомлять пользователя.
7. Два CTA: "Смотреть работы" (primary), "Выбрать тариф" (secondary).
8. Sticky mini-nav на mobile не нужен в MVP, чтобы не перегружать первый экран.

### 7.5 Работы учеников
1. На главной показывать 6 карточек максимум.
2. Карточка содержит название, кратко что сделано, результат, ссылку.
3. Карточки в 1 колонку на mobile, 2 на tablet, 3 на desktop.
4. Кнопка "Смотреть еще" ведет на /works.
5. На /works список с пагинацией или "Показать еще".

### 7.6 Тарифы
1. На mobile карточки тарифов вертикально (stack), без сложной таблицы.
2. В каждой карточке: название, для кого, что входит, формат, цена, CTA.
3. Один тариф может быть отмечен как "Рекомендуемый".
4. Нажатие "Выбрать тариф" прокручивает к форме и проставляет скрытое поле selected_tariff.
5. Формулировки преимуществ короткие, без воды, 4-6 пунктов максимум.

### 7.7 Форма заявки
1. Поля: Имя (обязательно), Контакт (обязательно), Цель обучения (опционально), Выбранный тариф (скрыто/авто).
2. Контакт в MVP: одно поле "Telegram или WhatsApp".
3. Кнопка submit фиксирована по ширине контейнера.
4. Под кнопкой чекбокс согласия с политикой (обязательно).
5. После отправки: success-state без ухода со страницы + трекинг события.

## 8. Telegram-бот и сумма заработка (логика данных)

### 8.1 Источник суммы
1. Ученик отправляет сумму в Telegram-бот.
2. Запись сохраняется в таблицу earnings_reports.
3. Запись получает статус pending.
4. Модератор подтверждает approved.
5. Только approved попадают в агрегированный total_earnings.

### 8.2 Минимальная модель данных
1. id.
2. student_id или анонимный идентификатор.
3. amount.
4. currency.
5. reported_at.
6. proof_url (опционально).
7. status (pending, approved, rejected).
8. approved_at, approved_by.

### 8.3 API (MVP)
1. GET /api/public/earnings/total возвращает total_usd, reports_count, updated_at.
2. GET /api/public/works?limit=&page= возвращает список работ.
3. GET /api/public/tariffs возвращает тарифы.
4. POST /api/public/leads принимает форму заявки.
5. POST /api/internal/bot/report принимает отчет из бота (внутренний endpoint).

### 8.4 Отображение суммы на сайте
1. Обновление при загрузке страницы.
2. Автообновление раз в 60 секунд в фоне.
3. Если есть техническая возможность, использовать push-механизм (SSE/WebSocket) для почти realtime-обновления total без перезагрузки.
4. Если API недоступен, показывать последнее кэшированное значение + метку "обновление временно недоступно".
5. Формат суммы по локали: 1 000 000 $ (единый формат на сайте).

## 9. Состояния интерфейса
1. Loading для суммы: skeleton + текст "Обновляем данные...".
2. Error для суммы: не ломать экран, показать fallback-значение.
3. Empty для работ: текст "Новые работы скоро появятся".
4. Form success: "Заявка отправлена, свяжемся с вами в течение N часов".
5. Form error: конкретная причина и сохранение введенных данных.

## 10. Валидации формы
1. Имя: от 2 символов, без спецмусора.
2. Контакт: проверка на Telegram-ник (@...) или номер телефона.
3. Ограничение длины текста цели: до 300 символов.
4. Антиспам: honeypot + rate limit на IP/contact.
5. Ошибки выводить под полем простым языком.

## 11. Accessibility (A11y)
1. Контраст текста и интерактивных элементов по WCAG AA.
2. Все кнопки и ссылки доступны с клавиатуры.
3. Явные focus-visible состояния.
4. aria-label для иконок и кнопок без текстовых меток.
5. Логичный порядок табуляции.
6. Уведомления success/error формы читаются скринридером (aria-live).
7. Для пользователей с prefers-reduced-motion отключать pulse/свечение/рывки счетчика и оставлять мягкое обновление числа без "wow"-эффектов.

## 12. SEO и метаданные
1. Уникальный title и description для / и /works.
2. OpenGraph для шаринга.
3. Индексируемый текст оффера и секций.
4. FAQ блок можно расширить до FAQ schema после MVP.
5. ЧПУ URL для кейсов на /works в следующей итерации.

## 14. Производительность (mobile приоритет)
1. LCP до 2.5s на 4G.
2. CLS до 0.1.
3. INP до 200ms.
4. Изображения работ в webp/avif, lazy-load ниже первого экрана.
5. Сумма и ключевой текст hero должны рендериться без блокировки тяжелым JS.
6. Анимации счетчика строить на transform/opacity (без layout thrashing и без частых reflow).
7. На устройствах с низкой производительностью автоматически снижать интенсивность эффектов (без заметных лагов и просадок FPS).

## 15. Контент для MVP (что подготовить)
1. Финальный оффер в 1-2 предложениях.
2. Подтвержденная стартовая сумма для hero.
3. Минимум 6 работ для главной.
4. Минимум 12-20 работ для /works.
5. Тексты по каждому тарифу.
6. Политика конфиденциальности и оферта.

## 16. Критерии приемки (Definition of Done)
1. Главный экран на mobile занимает ровно 100dvh и показывает динамическую сумму.
2. "Смотреть еще" из блока работ открывает /works.
3. Тариф, выбранный в карточке, попадает в форму.
4. Форма валидируется и отправляется в API, успех и ошибка обрабатываются корректно.
5. Сумма обновляется из API и имеет fallback при недоступности сервиса.
6. Основной пользовательский путь полностью работает на 390px без горизонтального скролла.
7. "Wow"-анимация суммы корректно отрабатывает на первом экране без фризов на 390px.
8. При новых данных во время сессии применяется micro-update без полного перезапуска hero-анимации.
9. При prefers-reduced-motion анимация упрощается и не вызывает дискомфорт.
10. Lighthouse mobile: Performance >=80, Accessibility >=90, Best Practices >=90, SEO >=90.

## 17. Design Direction (Modern Live, Raycast-style)
1. Визуальный характер: чистый, технологичный, премиальный, без визуального шума.
2. Принцип: один главный "вау"-акцент (сумма в Hero), остальной интерфейс спокойный и конверсионный.
3. Иерархия: крупные заголовки, короткие подзаголовки, минимальные абзацы, четкие CTA.
4. Пространство: много воздуха между блоками, без плотной "простыни" карточек.
5. Компоненты: аккуратные радиусы, ровные границы, мягкие тени, чистая сетка.
6. Запрещено: перегруженные фоны, хаотичные анимации, более 2 акцентных цветов в одном экране.

### 17.1 Принципы "живого" сайта
1. Motion должен поддерживать сценарий, а не отвлекать от действия.
2. На входе страницы: плавный reveal заголовка, потом запуск счетчика, потом CTA.
3. На скролле: легкие секционные reveal-анимации (opacity + translateY 12-20px).
4. На ховере/тапе: карточки слегка поднимаются (2-4px), кнопки дают визуальный отклик.
5. На обновлении суммы: заметное, но короткое изменение (delta-chip + pulse).

### 17.2 Motion tokens (для дизайна и разработки)
1. Duration xs: 120ms (tap/press states).
2. Duration sm: 200ms (hover/secondary transitions).
3. Duration md: 320ms (карточки/модальные изменения).
4. Duration lg: 600ms (reveal секций).
5. Duration xl: 1600-2200ms (count-up Hero).
6. Easing base: cubic-bezier(0.22, 1, 0.36, 1).
7. Easing exit: cubic-bezier(0.4, 0, 1, 1).

### 17.3 UI-паттерны по блокам
1. Hero: крупная сумма + короткий оффер + 2 CTA, без лишних декоративных элементов.
2. Works: карточки со стабильной высотой, обязательные поля "что сделали" и "результат", явная ссылка на кейс.
3. Tariffs: вертикальный стек на mobile, одна карточка "recommended", без сложных сравнительных таблиц в MVP.
4. Form: минимальное количество полей, мгновенная обратная связь, без тяжелых модалок.

### 17.4 Mobile-first поведение "живости"
1. На 390px анимации не должны ронять FPS; при просадке эффект упрощается автоматически.
2. Основной акцент движения только в Hero; ниже первого экрана motion менее интенсивный.
3. Состояния кнопок и полей должны быть заметны без hover (так как mobile-first).

## 19. Anti-Patterns (что не делать)
1. Не делать анимацию на каждом элементе в каждом блоке.
2. Не использовать тяжелый видеофон в Hero на mobile в MVP.
3. Не смешивать много разных визуальных стилей на одной странице.
4. Не превращать блок тарифов в сложную таблицу с мелким текстом.
5. Не прятать ключевую ценность (сумму и кейсы) ниже первого экрана.

## 20. Блок 2: Техническая спецификация для разработчика

### 20.1 Рекомендуемый стек (MVP)
1. Frontend: React + TypeScript (strict mode).
2. Сборка: Vite + SWC.
3. Стили: Tailwind CSS + clsx + tailwind-merge + class-variance-authority.
4. Роутинг: React Router.
5. Данные/API: TanStack Query (query + cache + retry + background refresh).
6. Формы: React Hook Form + Zod.
7. HTTP-клиент: native fetch + typed API layer.
8. Иконки: Lucide React (или аналогичный легковесный набор).
9. Пакетный менеджер: pnpm.
10. Node.js: LTS-версия.

### 20.2 Инструменты анимации (мощные, production-ready)
1. Motion for React (бывш. Framer Motion): основной инструмент для UI-анимаций, reveal и интерактивных состояний.
2. GSAP + ScrollTrigger: для сложных hero-сценариев и таймлайнов с точным контролем.
3. CountUp.js (или react-countup): для анимации денежных значений и дельта-обновлений.
4. Lenis (опционально): для контролируемого smooth-scroll, только после проверки mobile performance.
5. Lottie (опционально): для легких векторных анимаций без тяжелого видео.

### 20.3 Рекомендация по выбору анимационного стека
1. MVP: Motion for React + CountUp.js.
2. Расширенный hero (если нужен сильнее wow): точечно добавить GSAP только в первый экран.
3. Не смешивать одновременно несколько библиотек для одного и того же эффекта.
4. Учитывать prefers-reduced-motion на уровне глобальных motion-утилит.

### 20.4 Архитектура frontend (FSD v2.1, pages-first)
1. Базовый старт проекта: `app + pages + shared`; слои `widgets/features/entities` добавляются только при реальной переиспользуемости.
2. Правило направления импортов: `app -> pages -> widgets -> features -> entities -> shared`.
3. Запрещены cross-import между слайсами одного слоя.
4. Внешний импорт из слайса только через Public API (`index.ts`).
5. Если логика используется в одной странице, она остается в `pages/*` (не выносить преждевременно).

### 20.5 Типизация и качество кода
1. TypeScript strict: `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`.
2. Единый контракт API через DTO-типы и runtime-валидацию ответов (Zod).
3. ESLint + Prettier + lint-staged + Husky.
4. Запрет `any` без обоснования.
5. Критичные UI-компоненты покрывать story/example-кейсами.

### 20.6 API интеграция (frontend requirements)
1. `GET /api/public/earnings/total`:
   - Обновление: polling 60s.
   - Поддержка push (SSE/WebSocket) как enhancement.
2. `GET /api/public/works`:
   - Поддержка пагинации (`page`, `limit`) и сортировки по дате.
3. `GET /api/public/tariffs`:
   - Возвращает список активных тарифов.
4. `POST /api/public/leads`:
   - Идемпотентность по клиентскому request-id.
   - Нормальная обработка ошибок 4xx/5xx с UI-месседжами.

### 20.7 Состояния и отказоустойчивость
1. Для каждого асинхронного блока: loading, success, empty, error.
2. Hero-сумма должна иметь fallback-значение при недоступности API.
3. При сбое отправки формы данные в полях не теряются.
4. Ретраи для чтения данных ограничены и не должны блокировать UI.

### 20.8 Performance budget (mobile-first)
1. JS initial bundle: целевой бюджет до 220KB gzip для критического пути.
2. Hero-анимации не должны создавать layout thrashing.
3. Изображения кейсов: AVIF/WebP + lazy loading + responsive srcset.
4. Отложенная загрузка тяжелых animation dependencies (dynamic import).
5. Lighthouse mobile target: Perf >= 80, A11y >= 90, BP >= 90, SEO >= 90.

### 20.9 Тестирование
1. Unit: Vitest + Testing Library (утилиты форматирования суммы, валидация формы, ui-state).
2. Component/Integration: проверка hero-counter, тариф->форма, ошибки API.
3. E2E: Playwright (основной пользовательский путь от Hero до успешной отправки формы).
4. Отдельный e2e для prefers-reduced-motion сценария.
5. Smoke-test на 390px viewport перед релизом.

### 20.10 Observability и аналитика
1. Event tracking через GA4/PostHog (или выбранную платформу).
2. Логирование клиентских ошибок через Sentry (или аналог).
3. Отслеживать:
   - start/end hero animation;
   - click по CTA;
   - submit success/error;
   - переходы в /works и клики по работам.

### 20.11 CI/CD и окружения
1. Environments: dev, stage, prod.
2. CI pipeline:
   - install;
   - typecheck;
   - lint;
   - test;
   - build;
   - e2e smoke (для stage/prod predeploy).
3. Deploy: Vercel/Netlify/Cloudflare Pages (любой из approved вариантов).
4. Конфиги через env-переменные, без хардкода URL и ключей.
